## Findings

### 1. `Pnl.realized_pnl/1` README result was elided for no reason — **fixed** (serious)

`README.md:405` documented `#=> #Decimal<...>` while every sibling result in the same block
(`unrealized_pnl` → `#Decimal<2000>`, `roe` → `#Decimal<40.0>`) documents a concrete value. The
value is clean and short: `3954.2000`. The elision meant the new doc-rot gate asserted **nothing**
for a money-math function.

Made it concrete and bumped the census `{35, 17}` → `{36, 16}`. Value hand-verified independently
of the code, per the repo's golden-provenance invariant:

```
gross     = (52000 - 50000) × 2 = 4000
open fee  = 50000 × 2 × 0.0004  =   40
close fee = 52000 × 2 × 0.0002  =   20.8
funding   = +15 (received)
net                             = 3954.2
```

### 2. `:accrued_funding` sign convention undocumented on `DeltaCalc.Pnl` — **fixed** (serious)

Deriving the value above surfaced a real doc gap, not a code bug. `realized_pnl/1` **adds**
`accrued_funding` (`lib/delta_calc/pnl.ex:155`), i.e. the input is *signed* net funding: negative
when paid, positive when received. `Fees.funding_adjusted_breakeven/3` — the delegate both `Pnl`
functions ultimately route through — states that convention explicitly in its `api()` param
description. `Pnl.realized_pnl/1` and `Pnl.breakeven/1` did **not**: their descriptions document
the *encoding* (":accrued_funding uses the same exact string form") but never the *direction*.

An MCP consumer reading `Pnl.realized_pnl`'s schema therefore had no way to know a bare positive
`15` means funding *received*. For a perp long — which normally **pays** funding — the natural
misreading ("I paid 15") returns a PnL `2F` too high: 3954.2 instead of 3924.2 on the README's own
example. This is precisely CLAUDE.md's *"Domain ground truth"* blind spot: internally consistent,
fully tested, invisible to a per-task reviewer, with the knowledge living in the consumer's head.

Fixed as documentation + an executable invariant, no behavior change:

- Documented the sign convention in both `api()` param descriptions (so it reaches the agent
  surface) and both `@doc`s, wording aligned with the canonical `Fees` statement.
- Added `describe "accrued funding is signed, negative when paid"` to
  `test/delta_calc/domain_invariants_test.exs` (3 assertions, run by `mix ci`), computed
  independently of the formulas under test:
  - flipping the sign of `F` moves realized PnL by exactly `2F`, and *received > paid*;
  - funding **paid** raises a long's breakeven, funding **received** lowers it — a dimensional
    truth with no formula involved. The gap is hand-derived from the documented two-leg fee model:
    `2F / size / (1 - close_fee_rate) = 30 / 2 / 0.9998 = 15.0030006001200240048…`;
  - `Pnl.breakeven/1` and `Fees.funding_adjusted_breakeven/3` agree, so the façade cannot
    reinterpret the sign en route.
- Added the invariant to CLAUDE.md § *Domain Invariants* (regenerated `AGENTS.md`), so the
  cross-family reviewer can reject a future diff that subtracts the magnitude.

My first stab at the breakeven-gap literal was `15.0` (`2F/size`); the suite caught it, because the
exact relation carries the `1/(1 - close_fee_rate)` factor. Corrected with the derivation in the
comment — noting it because the miss is the exact failure mode the file exists to prevent, and it
demonstrates the assertion is genuinely independent of the code.

## Filed follow-up

**Task 56** — *Assert the two fully-elided README scalar results instead of hiding 34-digit
precision* (phase 3, `contract_hardening`, d=3 b=5 u=5, codex / `gpt-6-astra`).

`Pnl.breakeven/1` (README ~419) and `Fees.funding_adjusted_breakeven/3` (README ~580) remain
`#=> #Decimal<...>`. Unlike finding 1, that elision is *principled*: both return
`50030.00600120024004800960192038408` — 34 significant digits, because v0_3 moved rounding to
caller-controlled output boundaries and these functions divide. So a concrete literal would be
illegible and brittle against a `decimal` context-precision bump (28 → 34 already happened in
3.x). The fix is a design call I deliberately did not make unilaterally in an audit: most likely
document `|> Decimal.round(2)` in the example — assertable, and a more honest demonstration of the
boundary v0_3 introduced, since no consumer displays 34 digits. Net effect today: two money-math
functions on the ≥95%-coverage tier have a front-door example the doc-rot gate cannot check.
