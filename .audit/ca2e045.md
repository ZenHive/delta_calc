## Findings & fixes

### 1. (fixed) Six new modules missing from `DeltaCalc.Manifest`

All six modules carry `api()` annotations precisely so they surface through
`DeltaCalc.Manifest` + `Descripex.MCP.tools/1` — the agent-discovery contract CLAUDE.md
mandates ("`DeltaCalc.Manifest` + `Descripex.MCP.tools/1` aggregate the surface"). But
`@modules` in `manifest.ex` was never updated, so PnL, DeltaNeutral, PortfolioMargin,
StressScenario, Fees, and Carry were invisible to manifest/MCP consumers. The per-file
hooks couldn't catch this — it's a cross-module registration gap.

`ManifestTest` hard-codes the same list in three places, so the test passed today only
because both omissions agreed.

**Fix (forward):**
- `lib/delta_calc/manifest.ex` — appended the six modules to `@modules`.
- `test/delta_calc/manifest_test.exs` — updated `@expected_modules`, the `modules/0`
  exact-list assertion, and added one spot-check tool-name assertion per new module
  (matching the existing one-per-module pattern).

`mix test.json test/delta_calc/manifest_test.exs` → 5 passed, 0 failed.

### 2. (filed as task 26) `DeltaCalc.PnL` yields an awkward MCP tool prefix

Adding PnL to the manifest surfaced that Descripex underscores the module's last segment
via `Macro.underscore/1`, so `PnL` → `pn_l`, producing `pn_l__unrealized_pnl`,
`pn_l__realized_pnl`, etc. — inconsistent with every other module's clean single-token
prefix (`fees__`, `carry__`, `portfolio_margin__`). This is a public-surface naming
decision (override the short name vs rename the module), out of scope for a fix-forward,
so filed as **rmap task 26** (`consumer_math`, v0_3, assignee cursor). My manifest test
asserts the *actual* current name `pn_l__unrealized_pnl` so the suite stays green until
task 26 lands.
